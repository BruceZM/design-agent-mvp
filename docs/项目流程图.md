## 1. 系统长什么样

从网页、后端、模型到本地数据，先看清每一层负责什么。

```mermaid
flowchart TB
    accTitle: Design Agent MVP 系统架构
    accDescr: React 前端经 HTTP 调用 FastAPI；SQLite 保存任务与事件；串行 Worker 运行 LangGraph，使用 GLM 和受限工具修改独立 CRM worktree。
    subgraph FRONT[前端 · React + TypeScript + Vite]
        UI["材料上传 / 提交确认<br/>任务详情 / 差异 / 应用预览"]
    end
    subgraph BACK[后端 · FastAPI]
        API["HTTP API<br/>校验材料 / 幂等提交 / 查询任务"]
        WORKER["单线程串行 Worker<br/>从 SQLite 取 queued 任务"]
        GRAPH["LangGraph 工作流<br/>含 LangChain 开发 Agent"]
        API -->|唤醒| WORKER
        WORKER -->|逐个执行| GRAPH
    end
    subgraph MODEL[外部模型 · Coding Plan 兼容入口]
        GLM["glm-5.3-flash<br/>原图识别 / 开发计划 / 编码决策"]
    end
    subgraph LOCAL[本地数据与代码]
        DB[("SQLite<br/>任务快照 / revision / 事件 seq")]
        FILES["runtime/tasks/任务-id<br/>材料 / 设计说明 / 计划 / 日志 / 报告"]
        BASE["customer-manager · main<br/>固定 CRM 基线"]
        WT["runtime/worktrees/任务-id<br/>隔离分支 / src / 构建产物"]
        BASE -->|git worktree add| WT
    end
    UI -->|POST 上传 · GET 查询| API
    API -->|读写任务| DB
    GRAPH -->|阶段状态与事件| DB
    GRAPH -->|写入过程产物| FILES
    GRAPH -->|原图识别 / 计划 / 编码| GLM
    GRAPH -->|受限文件工具 / 固定检查| WT
    classDef base fill:#E1F4FF,stroke:#0878F9,color:#202B38,stroke-width:1.5px;
    classDef tool fill:#E8E6FF,stroke:#7966E8,color:#202B38,stroke-width:1.5px;
    class UI,API,WORKER,GRAPH,GLM,DB,FILES,BASE,WT base;
    class GRAPH tool;
    style FRONT fill:#F5F7FA,stroke:#C6CDD5
    style BACK fill:#F5F7FA,stroke:#C6CDD5
    style MODEL fill:#F5F7FA,stroke:#C6CDD5
    style LOCAL fill:#F5F7FA,stroke:#C6CDD5
```

- 前端通过 HTTP 提交与轮询。任务详情在 queued / running 时每 3 秒查询一次；网络失败时最多退避到 15 秒。
- 单线程 Worker 从 SQLite 按创建时间取任务；没有 Celery、Redis、向量库或 RAG。
- GLM 负责识图、规划和编码决策；文件读写、Git 与检查命令由本地代码执行。

源码：[main.py](../design-agent/backend/app/main.py)、[worker.py](../design-agent/backend/app/worker.py)、[store.py](../design-agent/backend/app/store.py)。独立矢量图：[SVG](flows/svg/01-architecture.svg)。

## 2. 一次上传如何变成后台任务

提交请求不等待模型开发结束；前端拿到任务 ID 后独立查询执行进度。

```mermaid
sequenceDiagram
    accTitle: 从上传到后台交付的任务时序
    accDescr: 提交请求返回任务 ID 后，Worker 独立执行；前端每三秒读取 SQLite 快照，结束后查看差异、报告和预览。
    actor U as 用户
    participant F as React 前端
    participant A as FastAPI
    participant S as SQLite
    participant W as 串行 Worker
    participant G as LangGraph 工作流
    U->>F: 上传设计稿 + PRD，确认提交
    F->>A: POST /api/tasks + idempotency_key
    A->>A: 校验文件、解析 PRD、计算材料指纹
    A->>S: 检查提交标识
    alt 同一标识且材料一致
        S-->>A: 已存在的任务
        A-->>F: 202，返回已有任务
    else 首次提交
        A->>A: 保存原始材料到 runtime/tasks
        A->>S: 写入 queued 任务与首条事件
        A->>W: notify 唤醒
        A-->>F: 202 + 任务 ID
    end
    F-->>U: 跳转任务详情页
    W->>S: 查询最早的 queued 任务
    S-->>W: 任务 ID
    W->>G: Workflow.run()
    loop queued / running 时每 3 秒
        F->>A: GET /api/tasks/任务-id
        A->>S: 读取快照与事件
        S-->>A: status / phase / revision / events
        A-->>F: 任务数据 + 可用产物列表
        F-->>U: 更新阶段、日志与检查结果
        G->>S: 持续写入阶段状态与事件
    end
    G->>S: 写入 succeeded 或 failed
    G-->>W: 当前任务结束，继续下一条
    F->>A: 获取最终快照
    A-->>F: 终态、差异、报告与可用预览
    F-->>U: 停止常规轮询，展示交付结果
    Note over F,W: 关闭网页不停止后台任务；后端进程停止会中断执行
    Note over A,S: 同一标识但材料改变返回 409；上传校验失败不创建任务
```

- 材料验证与任务写入发生在返回 202 之前；Worker 唤醒通知不是持久化队列，queued 状态保存在 SQLite。
- 提交响应丢失时，前端用同一提交标识查询 /api/submissions，再决定是否重试，避免重复创建任务。
- 后端重启会把原 running 任务标记 failed / interrupted，保留已有产物；queued 任务继续排队，不从中断节点恢复。

源码：[App.tsx](../design-agent/frontend/src/App.tsx)、[main.py](../design-agent/backend/app/main.py)、[worker.py](../design-agent/backend/app/worker.py)。独立矢量图：[SVG](flows/svg/02-sequence.svg)。

## 3. LangGraph 工作流怎么转

六个真实节点串起开发流程；判断菱形展开了检查路由与交付节点内部的逻辑。

```mermaid
flowchart TB
    accTitle: LangGraph 六节点工作流与有限修复
    accDescr: 检查失败时最多返回开发一次，随后进入交付；只有检查通过且有源文件变化才创建成功提交。任意阶段异常保存失败信息。
    START([START]) --> M["materials · 材料解析<br/>PRD 提取 + GLM 原图识别"]
    M --> P["prepare · 仓库准备<br/>从 main 创建分支与 worktree"]
    P --> L["plan · 开发计划<br/>GLM 输出 JSON，校验文件权限"]
    L --> D["develop · 编码<br/>LangChain 模型与工具循环"]
    D --> C["check · 独立检查<br/>typecheck + build；attempt 加 1"]
    C --> OK{"检查通过？"}
    OK -->|否| R{"可再修复？"}
    R -->|是 · 默认最多 1 轮| D
    OK -->|是| V
    R -->|否| V
    subgraph DELIVERY[deliver · 交付节点的内部判断]
        V["保存 changes.diff<br/>整理检查结果"] --> PASS{"通过且有改动？"}
        PASS -->|是| COMMIT["创建本地 Git 提交<br/>写入 succeeded 报告"]
        PASS -->|否| FAIL["保留失败分支与报告<br/>写入 failed；不提交"]
    end
    COMMIT --> END([END])
    FAIL --> END
    ERR["阶段异常 / 预算耗尽<br/>保存失败信息与已有差异"] -.-> END
    M -.异常示例.-> ERR
    D -.异常示例.-> ERR
    classDef base fill:#E1F4FF,stroke:#0878F9,color:#202B38,stroke-width:1.5px;
    classDef decision fill:#FFF3C7,stroke:#F5A623,color:#202B38,stroke-width:1.5px;
    classDef tool fill:#E8E6FF,stroke:#7966E8,color:#202B38,stroke-width:1.5px;
    classDef success fill:#E4F4E8,stroke:#348456,color:#202B38,stroke-width:1.5px;
    classDef failure fill:#FFE9E9,stroke:#CC5454,color:#202B38,stroke-width:1.5px;
    class START,END,M,P,L,C,V base;
    class D tool;
    class OK,R,PASS decision;
    class COMMIT success;
    class FAIL,ERR failure;
    style DELIVERY fill:#F5F7FA,stroke:#C6CDD5
```

- 外层实际节点是 materials、prepare、plan、develop、check、deliver；条件判断不是额外的持久化节点。
- 默认 max_repairs=1：首次检查失败后最多修复一轮，再次检查后一定进入交付。
- succeeded 只表示有源码改动且 typecheck / build 通过。浏览器功能和视觉检查在报告中仍标记 not_run。

源码：[workflow.py](../design-agent/backend/app/workflow.py)、[config.py](../design-agent/backend/app/config.py)。独立矢量图：[SVG](flows/svg/03-langgraph.svg)。

## 4. 模型怎样真正改动代码

这是 develop 节点内部由 LangChain create_agent 组织的循环，与外层六节点工作流分开理解。

```mermaid
flowchart TB
    accTitle: 编码 Agent 内部的模型与工具循环
    accDescr: 预载需求、计划与源码后，先检查模型调用预算；模型返回工具调用时由本地工具执行并回传结果，无工具调用时返回摘要。
    CONTEXT["输入开发上下文<br/>PRD / 设计说明 / 计划<br/>预载 README 与相关源码"] --> B{"预算与时间可用？"}
    B -->|是| MODEL["调用 glm-5.3-flash<br/>保留 reasoning_content"]
    B -->|否| ERROR["抛出异常<br/>交给外层工作流保存失败"]
    MODEL --> Q{"返回 tool_calls？"}
    Q -->|有| TOOLS["本地 tools 执行<br/>list_files / read_file<br/>write_file / replace_text<br/>run_check"]
    TOOLS --> RESULT["ToolMessage 回传<br/>文件内容 / 操作结果 / 拒绝原因"]
    RESULT --> B
    Q -->|没有| SUMMARY(["返回中文开发摘要<br/>外层继续独立 check"])
    classDef base fill:#E1F4FF,stroke:#0878F9,color:#202B38,stroke-width:1.5px;
    classDef decision fill:#FFF3C7,stroke:#F5A623,color:#202B38,stroke-width:1.5px;
    classDef tool fill:#E8E6FF,stroke:#7966E8,color:#202B38,stroke-width:1.5px;
    classDef failure fill:#FFE9E9,stroke:#CC5454,color:#202B38,stroke-width:1.5px;
    class CONTEXT,MODEL,RESULT,SUMMARY base;
    class B,Q decision;
    class TOOLS tool;
    class ERROR failure;
```

- 模型返回工具调用请求，本地执行五种白名单工具，然后将结果作为 ToolMessage 交还模型。
- 默认预算为计划与编码合计最多 16 次模型调用；计时从 Developer 创建开始。材料识图另有一次请求与 110 秒外层超时。
- 只可读取 README 与 src；只可写 src 中的 TS / TSX / CSS。SDK 不自动重试，工具之间保留 GLM reasoning_content。

源码：[agent.py](../design-agent/backend/app/agent.py)、[models.py](../design-agent/backend/app/models.py)、[repository.py](../design-agent/backend/app/repository.py)。独立矢量图：[SVG](flows/svg/04-tool-loop.svg)。

## 5. 分支、预览与远程交付

本地 CRM 的隔离开发，与整个项目在一个 GitHub 公开仓库中的展示，是两个不同步骤。

```mermaid
flowchart TB
    accTitle: 本地 Git 隔离开发与一个远程仓库的交付关系
    accDescr: Agent 自动在 CRM worktree 中开发并提交成功结果；公开仓库中的统一目录和任务分支由人工整理推送，不属于后台自动流程。
    subgraph LOCAL[Agent 自动执行 · 本地 CRM 仓库]
        BASE["customer-manager · main<br/>固定开发基线"] --> WT["新建 design-agent/任务-id<br/>独立 worktree，共用已安装依赖"]
        WT --> CODE["修改 src/ 内 TS / TSX / CSS<br/>执行固定编译与构建检查"]
        CODE --> GATE{"有改动且检查通过？"}
        GATE -->|是| COMMIT["创建本地 Git 提交<br/>记录成功交付"]
        GATE -->|否| KEEP["保留分支、差异和失败报告<br/>不创建成功提交"]
        COMMIT --> ART["交付 changes.diff 与报告<br/>build 通过时提供本地预览"]
        KEEP --> ART
    end
    subgraph REMOTE[GitHub · 一个远程公开仓库]
        MAIN["design-agent-mvp · main<br/>Agent + CRM 基线 + mock + 设计资料"]
        TASK["design-agent/任务-id<br/>统一目录下的 CRM 需求成果"]
        MAIN -->|同一基线下比较| TASK
    end
    BASE -.人工整理整个项目并发布.-> MAIN
    COMMIT -.人工转存源码差异并推送.-> TASK
    ART --> REVIEW["人工浏览器与视觉验收<br/>检查交互、功能与设计还原"]
    classDef base fill:#E1F4FF,stroke:#0878F9,color:#202B38,stroke-width:1.5px;
    classDef decision fill:#FFF3C7,stroke:#F5A623,color:#202B38,stroke-width:1.5px;
    classDef success fill:#E4F4E8,stroke:#348456,color:#202B38,stroke-width:1.5px;
    classDef failure fill:#FFE9E9,stroke:#CC5454,color:#202B38,stroke-width:1.5px;
    class BASE,WT,CODE,ART,MAIN,TASK,REVIEW base;
    class GATE decision;
    class COMMIT success;
    class KEEP failure;
    style LOCAL fill:#F5F7FA,stroke:#C6CDD5
    style REMOTE fill:#F5F7FA,stroke:#C6CDD5
```

- Agent 从 customer-manager 的固定 main 创建 worktree；依赖以本地符号链接共用，模型不能修改依赖或 Git。
- 当前后台交付只保存本地分支、差异、报告与可用预览；remote_pushed=false，不自动推送、合并或部署。
- 现有公开仓库和三个成果分支由人工整理同步。图中虚线表示人工步骤，不应介绍成 Agent 已实现的自动能力。

源码：[repository.py](../design-agent/backend/app/repository.py)、[workflow.py](../design-agent/backend/app/workflow.py)、[任务分支说明.md](../docs/任务分支说明.md)。独立矢量图：[SVG](flows/svg/05-git-delivery.svg)。

## 格式与维护

HTML 用于展示，Markdown 用于阅读和版本维护，SVG 用于放入文档与演示。HTML 已嵌入矢量图，没有运行时 CDN 依赖。

修改 `docs/flows/sources/*.mmd` 与 `diagrams.json` 后，使用独立的 [Mermaid CLI](https://github.com/mermaid-js/mermaid-cli) 重新生成；工具支持 SVG、PNG 与 PDF 渲染。

```sh
npm install --prefix .publish/diagram-tools --no-save @mermaid-js/mermaid-cli@12.0.0
python3 scripts/build-flow-docs.py --renderer .publish/diagram-tools/node_modules/.bin/mmdc
```

若使用系统 Chrome 而不下载 Puppeteer 浏览器，可为 CLI 提供 `--puppeteer-config` JSON，其中设置 `executablePath` 为本机 Chrome 路径。文档工具安装在被 Git 忽略的 `.publish/`，不会改变 Agent 的运行依赖。
