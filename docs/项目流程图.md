## 1. 系统长什么样

从网页、后端、模型到本地数据，先看清每一层负责什么。

```mermaid
flowchart TB
    accTitle: Design Agent MVP 系统架构
    accDescr: React 经 HTTP 调用 FastAPI；后端的串行 Worker 执行 LangGraph，调用 GLM 和本地工具；SQLite 与任务目录保存状态和产物，CRM worktree 隔离源码改动。
    subgraph FRONT[用户工作台]
        UI["React + TypeScript<br/>上传 / 进度 / 差异 / 预览"]
    end
    subgraph BACK[后端 · FastAPI]
        direction LR
        API["HTTP API<br/>校验 / 幂等 / 查询"] -->|notify| WORKER["串行 Worker<br/>读取 queued 任务"]
        WORKER -->|run| GRAPH["LangGraph<br/>六阶段 + 开发 Agent"]
    end
    subgraph MODEL[模型服务]
        GLM["glm-5.3-flash<br/>识图 / 计划 / 编码"]
    end
    subgraph DATA[任务数据]
        direction LR
        DB[("SQLite<br/>任务快照 / 事件")]
        FILES["runtime/tasks<br/>材料 / 日志 / 报告"]
        DB ~~~ FILES
    end
    subgraph REPO[本地 CRM]
        direction LR
        BASE["main<br/>固定基线"] -->|创建| WT["独立 worktree<br/>分支 / src / dist"]
    end
    FRONT -->|HTTP 上传 / 查询| BACK
    BACK -->|模型调用| MODEL
    BACK -->|读写快照与产物| DATA
    BACK -->|工具 / 检查 / 预览| REPO
    classDef base fill:#E1F4FF,stroke:#0878F9,color:#202B38,stroke-width:1.5px;
    classDef tool fill:#E8E6FF,stroke:#7966E8,color:#202B38,stroke-width:1.5px;
    class UI,API,WORKER,GLM,DB,FILES,BASE,WT base;
    class GRAPH tool;
    style FRONT fill:#F5F7FA,stroke:#C6CDD5
    style BACK fill:#F5F7FA,stroke:#C6CDD5
    style MODEL fill:#F5F7FA,stroke:#C6CDD5
    style DATA fill:#F5F7FA,stroke:#C6CDD5
    style REPO fill:#F5F7FA,stroke:#C6CDD5
```

- 前端通过 HTTP 提交与轮询。任务详情在 queued / running 时每 3 秒查询一次；网络失败时最多退避到 15 秒。
- 单线程 Worker 从 SQLite 按创建时间取任务；没有 Celery、Redis、向量库或 RAG。
- GLM 负责识图、规划和编码决策；文件读写、Git 与检查命令由本地代码执行。

源码：[main.py](../design-agent/backend/app/main.py)、[worker.py](../design-agent/backend/app/worker.py)、[store.py](../design-agent/backend/app/store.py)。独立矢量图：[SVG](flows/svg/01-architecture.svg)。

## 2. 一次上传如何变成后台任务

提交请求不等待模型开发结束；前端拿到任务 ID 后独立查询执行进度。

```mermaid
sequenceDiagram
    accTitle: 上传、后台执行与 HTTP 轮询
    accDescr: 新提交持久化后唤醒 Worker 并返回 202；Worker 串行运行工作流，前端轮询状态。提交 key 支持幂等重试。
    participant F as 用户 / React 前端
    participant A as FastAPI
    participant S as SQLite
    participant W as 串行 Worker
    participant G as LangGraph
    F->>A: 确认上传：设计稿 + PRD + 提交 key
    Note over A,S: 校验材料；同 key 同材料返回原任务，冲突返回 409
    A->>S: 材料落盘后写 queued 任务与事件
    A->>W: notify 唤醒
    A-->>F: 202 + 任务 ID
    W->>G: 取 queued 后串行 Workflow.run()
    loop 查询至任务终态
        G->>S: 写入阶段状态 / 事件 / 最终结果
        F->>A: GET 任务快照（正常约每 3 秒）
        A->>S: 读取任务与日志
        A-->>F: 快照 / 日志 / 已生成的交付文件
    end
    Note over F,G: 读到终态后停止轮询；Worker 继续下一条；关闭网页不停止后台任务
```

- 材料验证与任务写入发生在返回 202 之前；Worker 唤醒通知不是持久化队列，queued 状态保存在 SQLite。
- 提交响应丢失时，前端用同一提交标识查询 /api/submissions，再决定是否重试，避免重复创建任务。
- 后端重启会把原 running 任务标记 failed / interrupted，保留已有产物；queued 任务继续排队，不从中断节点恢复。

源码：[App.tsx](../design-agent/frontend/src/App.tsx)、[main.py](../design-agent/backend/app/main.py)、[worker.py](../design-agent/backend/app/worker.py)。独立矢量图：[SVG](flows/svg/02-sequence.svg)。

## 3. LangGraph 工作流怎么转

六个真实节点按三组排布；组内显示检查修复和交付判断，分组用于阅读。

```mermaid
flowchart TB
    accTitle: LangGraph 六节点工作流与有限修复
    accDescr: 输入阶段依次解析材料、准备仓库和计划；编码检查阶段默认最多修复一次；交付阶段通过且有改动才提交。分组用于排版，不是额外的持久化节点。
    subgraph INPUT[1 · 输入与计划]
        direction LR
        START([START]) --> M["materials<br/>PRD + 原图识别"]
        M --> P["prepare<br/>main → worktree"]
        P --> L["plan<br/>JSON + 权限校验"]
    end
    subgraph EXEC[2 · 编码与检查]
        direction LR
        D["develop<br/>模型 + 工具循环"] -->|check · 固定检查| C{"检查通过？"}
        C -->|是| READY([进入交付])
        C -->|否| R{"可再修复？"}
        R -->|是 · 默认 1 次| D
        R -->|否| READY
    end
    subgraph DELIVERY[3 · 本地交付]
        direction LR
        V["deliver<br/>保存差异 / 报告<br/>通过且有改动才提交"] --> END([END])
    end
    INPUT --> EXEC
    EXEC --> DELIVERY
    classDef base fill:#E1F4FF,stroke:#0878F9,color:#202B38,stroke-width:1.5px;
    classDef decision fill:#FFF3C7,stroke:#F5A623,color:#202B38,stroke-width:1.5px;
    classDef tool fill:#E8E6FF,stroke:#7966E8,color:#202B38,stroke-width:1.5px;
    class START,END,M,P,L,V,READY base;
    class D tool;
    class C,R decision;
    style INPUT fill:#F5F7FA,stroke:#C6CDD5
    style EXEC fill:#F5F7FA,stroke:#C6CDD5
    style DELIVERY fill:#F5F7FA,stroke:#C6CDD5
```

- 实际节点只有 materials、prepare、plan、develop、check、deliver；图中的分组、进入交付标记和条件判断不是额外的持久化节点。
- 默认 max_repairs=1：首次检查失败后最多修复一轮，再次检查后一定进入交付。
- succeeded 只表示有源码改动且 typecheck / build 通过。浏览器功能和视觉检查在报告中仍标记 not_run。
- 任意阶段异常或预算耗尽由 Workflow.run 的外层异常处理保存错误、差异和失败报告，不自动重提任务。

源码：[workflow.py](../design-agent/backend/app/workflow.py)、[config.py](../design-agent/backend/app/config.py)。独立矢量图：[SVG](flows/svg/03-langgraph.svg)。

## 4. 模型怎样真正改动代码

这是 develop 节点内部由 LangChain create_agent 组织的循环，与外层六节点工作流分开理解。

```mermaid
flowchart LR
    accTitle: 编码 Agent 内部的模型与工具循环
    accDescr: 预载需求、计划与源码后，先检查模型调用预算；模型返回工具调用时由本地工具执行并回传结果，无工具调用时返回摘要。
    CONTEXT["开发上下文<br/>需求 / 设计 / 计划 / 源码"] --> B{"预算 / 时间可用？"}
    B -->|是| MODEL["GLM 调用<br/>保留思考上下文"]
    B -->|否| ERROR["抛出异常<br/>外层保存失败"]
    MODEL --> Q{"返回 tool_calls？"}
    Q -->|有| TOOLS["本地工具执行<br/>list_files / read_file<br/>write_file / replace_text<br/>run_check"]
    TOOLS --> RESULT["ToolMessage<br/>结果 / 拒绝原因"]
    RESULT --> B
    Q -->|没有| SUMMARY(["开发摘要<br/>外层独立 check"])
    classDef base fill:#E1F4FF,stroke:#0878F9,color:#202B38,stroke-width:1.5px;
    classDef decision fill:#FFF3C7,stroke:#F5A623,color:#202B38,stroke-width:1.5px;
    classDef tool fill:#E8E6FF,stroke:#7966E8,color:#202B38,stroke-width:1.5px;
    classDef failure fill:#FFE9E9,stroke:#CC5454,color:#202B38,stroke-width:1.5px;
    class CONTEXT,MODEL,RESULT,SUMMARY base;
    class B,Q decision;
    class TOOLS tool;
    class ERROR failure;
```

- 模型返回工具调用请求，本地执行五种白名单工具，然后将结果作为 ToolMessage 交还模型。
- 默认预算为计划与编码合计最多 16 次模型调用；计时从 Developer 创建开始。材料识图另有一次请求与 110 秒外层超时。
- 只可读取 README 与 src；只可写 src 中的 TS / TSX / CSS。SDK 不自动重试，工具之间保留 GLM reasoning_content。

源码：[agent.py](../design-agent/backend/app/agent.py)、[models.py](../design-agent/backend/app/models.py)、[repository.py](../design-agent/backend/app/repository.py)。独立矢量图：[SVG](flows/svg/04-tool-loop.svg)。

## 5. 分支、预览与远程交付

本地 CRM 的隔离开发，与整个项目在一个 GitHub 公开仓库中的展示，是两个不同步骤。

```mermaid
flowchart TB
    accTitle: 本地隔离开发与一个远程仓库的交付关系
    accDescr: 本地 CRM 任务分支由 Agent 自动开发与检查，通过且有改动才提交；GitHub 的统一目录和成果分支由人工同步，最终功能与视觉由人工验收。
    subgraph LOCAL[Agent 自动执行 · 本地 CRM]
        direction LR
        BASE["CRM main<br/>固定基线"] --> WT["任务分支<br/>独立 worktree"]
        WT --> CODE["修改 src<br/>typecheck + build"]
        CODE --> GATE{"有改动<br/>且检查通过？"}
        GATE -->|是| COMMIT["本地提交<br/>succeeded"]
        GATE -->|否| KEEP["保留分支<br/>failed；不提交"]
        COMMIT --> ART["差异 / 报告<br/>构建通过可预览"]
        KEEP --> ART
    end
    subgraph REMOTE[GitHub · 一个公开仓库]
        direction LR
        MAIN["design-agent-mvp · main<br/>Agent + CRM 基线 + mock"]
        TASK["design-agent/任务-id<br/>CRM 需求成果"]
        MAIN -->|比较源码| TASK
    end
    LOCAL -.项目与成功成果人工同步.-> REMOTE
    LOCAL -->|查看交付| REVIEW["人工功能与视觉验收<br/>交互 / 需求 / 设计还原"]
    classDef base fill:#E1F4FF,stroke:#0878F9,color:#202B38,stroke-width:1.5px;
    classDef decision fill:#FFF3C7,stroke:#F5A623,color:#202B38,stroke-width:1.5px;
    classDef success fill:#E4F4E8,stroke:#348456,color:#202B38,stroke-width:1.5px;
    classDef failure fill:#FFE9E9,stroke:#CC5454,color:#202B38,stroke-width:1.5px;
    class BASE,WT,CODE,ART,MAIN,TASK,REVIEW base;
    class GATE decision;
    class COMMIT success;
    class KEEP failure;
    style LOCAL fill:#F5F7FA,stroke:#C6CDD5
    style REMOTE fill:#F5F7FA,stroke:#C6CDD5
```

- Agent 从 customer-manager 的固定 main 创建 worktree；依赖以本地符号链接共用，模型不能修改依赖或 Git。
- 当前后台交付只保存本地分支、差异、报告与可用预览；remote_pushed=false，不自动推送、合并或部署。
- 现有公开仓库和三个成果分支由人工整理同步。图中虚线表示人工步骤，不应介绍成 Agent 已实现的自动能力。

源码：[repository.py](../design-agent/backend/app/repository.py)、[workflow.py](../design-agent/backend/app/workflow.py)、[任务分支说明.md](../docs/任务分支说明.md)。独立矢量图：[SVG](flows/svg/05-git-delivery.svg)。

## 格式与维护

HTML 用于展示，Markdown 用于阅读和版本维护，SVG 用于放入文档与演示。HTML 已嵌入矢量图，没有运行时 CDN 依赖。

修改 `docs/flows/sources/*.mmd` 与 `diagrams.json` 后，使用独立的 [Mermaid CLI](https://github.com/mermaid-js/mermaid-cli) 重新生成；工具支持 SVG、PNG 与 PDF 渲染。

```sh
npm install --prefix .publish/diagram-tools --no-save @mermaid-js/mermaid-cli@12.0.0
python3 scripts/build-flow-docs.py --renderer .publish/diagram-tools/node_modules/.bin/mmdc
```

若使用系统 Chrome 而不下载 Puppeteer 浏览器，可为 CLI 提供 `--puppeteer-config` JSON，其中设置 `executablePath` 为本机 Chrome 路径。文档工具安装在被 Git 忽略的 `.publish/`，不会改变 Agent 的运行依赖。
