# Design Agent 代码阅读指南

这份指南对应当前本地 MVP。先打开 [五张项目流程图](../../docs/flows/index.html)，再在 VS Code 中打开 `design-agent-mvp.code-workspace`，沿下面的顺序阅读。注释解释职责、关键写法、设计理由和实际限制，不改变执行逻辑。下游 `customer-manager/` 业务源码本次没有修改。

## 1. 先认识三个运行位置

| 位置 | 负责什么 | 从哪里开始读 |
| --- | --- | --- |
| 浏览器里的 React | 选择文件、确认提交、轮询、展示日志与交付 | [App.tsx](../frontend/src/App.tsx) |
| FastAPI 进程 | 校验上传、持久化任务、返回 API 和静态文件 | [main.py](../backend/app/main.py) |
| 同进程的后台线程 | 串行跑工作流，调用模型和本地工具 | [worker.py](../backend/app/worker.py) |

前端并不执行大模型，也不直接改仓库。HTTP 上传返回 `202 + 任务 ID` 后，Worker 才持续处理长任务；页面随后用 GET 获取最新记录。因此关闭网页不影响任务，停止后端进程会中断任务。

## 2. 推荐阅读顺序

在 VS Code 按 `Cmd+P` 搜索文件，按 `Cmd+Shift+O` 查找文件内的函数/类；对符号使用“转到定义”追踪调用。第一次先看模块顶部和函数前注释，再进入函数体，不必从所有 import 开始逐行背诵。

| --- | --- | --- |

## 3. 跟踪一次真实提交

1. `UploadCard` 把 `File` 交给 `NewTask` 保存。图片用 object URL 本地预览，此时没有上传；文件改变时 effect 清理旧 URL。
2. `validate()` 检查文件名和大小，打开原生 `dialog` 确认框。用户确认后 `submit()` 才组装 `FormData`，写入稳定的 `idempotency_key`。
3. `request()` POST 到 `/api/tasks`。`guard_upload()` 限制请求总量；`documents.py` 验证图片真实格式并提取 PRD，不能只相信前端扩展名。
4. 后端计算材料指纹，在同一进程锁内查找 key。相同 key、相同材料返回已有任务；相同 key、不同材料返回 409。
5. 保存 `runtime/tasks/<id>/design.*` 和 `prd`，写入 SQLite 的 queued 任务与首条事件，再 `worker.notify()`。
6. 前端拿到 ID 后跳转 `/tasks/<id>`。Worker 读取最早 queued 任务，调用 `Workflow.run()`；前端仅观察，不推动执行。

**为什么有 key 和 fingerprint 两个值？** key 标记“一次提交意图”，fingerprint 标记“本次材料内容”。如果服务器已创建任务但响应在网络中丢失，只按文件名或禁用按钮都无法避免再次创建。页面会先 GET `/api/submissions/<key>` 找回，再决定是否重试。材料改变但沿用同 key，则明确冲突，不悄悄当成旧任务。

## 4. LangGraph 的六个节点

`StateGraph(State)` 声明状态形状，`add_node` 注册函数，`add_edge` 连接固定顺序，`add_conditional_edges` 选择修复或交付。节点返回部分字典，框架将结果合并到已有状态。

| 节点 | 输入与操作 | 输出 / 产物 |
| --- | --- | --- |
| `materials` | 读取原始材料、附加补充说明、等待多模态识图 | `prd`、`design_spec`、`attempt=0`；两份 Markdown |
| `prepare` | 从 CRM 的 main 创建任务分支和 worktree，建立 Developer | 分支/基线/路径写 SQLite |
| `plan` | 模型返回 JSON，Pydantic 校验字段，校验写入路径 | `plan`；`plan.json` |
| `develop` | 预载源码，运行内部模型/工具循环；修复时附带失败输出 | `summary`；`agent-summary.md` |
| `check` | 独立执行 typecheck 和 build，不采信模型自述 | `checks`、`attempt+1`；两份日志 |
| `deliver` | 保存 diff；有改动且检查通过才本地 commit | succeeded/failed；JSON 与 Markdown 报告 |

例如 `max_repairs=1`：首次开发 → 检查后 `attempt=1` → 失败时返回 develop 一次 → 再检查后 `attempt=2` → 即使仍失败也进入 deliver。`attempt` 是检查轮数，报告中的 `repair_rounds` 是 `attempt - 1`，两者不要混淆。

`State` 是这一次图执行的内存数据；SQLite 是页面可查询的持久化记录。本版本没有 LangGraph checkpointer。重启不会从某个节点继续跑，也不会自动重复模型调用：最近任务中的旧 running 会标记为 interrupted，queued 可继续排队执行。

## 5. 三类模型工作与真正的工具执行

当前默认都由 GLM 完成模型推理，但分为三次用途：

- `describe_image()` 将原图转成 `data:image/...;base64,...`，与解析提示一起发送，得到中文视觉说明。编码阶段使用这份说明，不在每轮发送原图。
- `Developer.plan()` 请求 JSON 计划。JSON mode 帮助输出合法对象，Pydantic 校验字段，Repository 再校验文件权限，三层各管一件事。
- `Developer.develop()` 用 LangChain `create_agent()` 进入模型与工具循环。模型返回 `tool_calls` 时，框架调用对应 Python 工具，将结果作为 `ToolMessage` 回传；没有工具调用时返回摘要。

外层六阶段图与内部模型/工具图是两层流程。前者决定什么时候解析、开发、检查和交付；后者决定这一轮读取哪个文件、替换哪段文本。不能把整个项目描述为一个没有边界的“模型自由执行”。

| 模型工具 | Python 真正执行的操作 | 为什么这样限制 |
| --- | --- | --- |
| `list_files` | 列 README 与允许的源文件 | 帮助发现现有组件，避免凭空猜文件名 |
| `read_file` | 经路径校验读取文件 | 修改前了解现有功能 |
| `write_file` | 写允许路径中的完整内容 | 支持创建文件，限制单文件大小 |
| `replace_text` | 旧片段恰好匹配一次才替换 | 适合局部修改，避免误改重复代码 |
| `run_check` | 执行预定义的 typecheck/build | 模型不能传任意 shell 命令 |

`@tool` 的函数名、类型标注和 docstring 形成模型可见的工具描述，因此工具 docstring 属于执行协议，不随意改写。`safely()` 将可纠正的文件错误返回给模型；严重错误、预算耗尽和模型异常由外层任务边界保存为失败。

`GLMChatOpenAI` 继承的是 OpenAI 兼容协议适配器，实际服务由 `base_url/model` 决定。`_create_chat_result()` 保留响应中的 `reasoning_content`，`_get_request_payload()` 在下一轮 assistant 历史中重新发送，避免工具往返丢失 GLM 扩展上下文。当前覆盖非流式路径；依赖版本锁定，升级框架时应运行协议测试。

## 6. 预算与超时分别管什么

| 配置 / 限制 | 当前范围 |
| --- | --- |
| `MAX_MODEL_CALLS=16` | 同一 Developer 的计划、编码、修复调用总数；不包含视觉调用 |
| `TASK_TIMEOUT_SECONDS=900` | Developer 建立后，在每次模型调用前检查经过时间；不是整条任务的强制取消机制 |
| 模型客户端 `timeout=90` | 单个模型 HTTP 请求 |
| 视觉外层 110 秒 | 一次异步视觉调用 |
| `max_retries=0` | 关闭 SDK 模型请求自动重试；与检查失败后的代码修复不同 |
| 检查 100 秒 | 每次 npm typecheck/build 命令 |
| 内部 `recursion_limit=45`、外层 25 | 图执行步数；不是 token 数或模型调用次数 |

`wrap_model_call` 中间件在真实编码请求前消耗预算，修复继续使用同一预算。`total_tokens` 只累计模型返回的使用量元数据，不是本地精确计费表。

## 7. Git、权限和交付

`Repository.prepare()` 从 CRM main 的固定提交创建 `design-agent/<id>` 和独立 worktree。源码写入工作目录，不修改 CRM 主目录。`node_modules` 复用使用者预装的依赖，模型不安装新包。

`Repository.path()` 同时校验相对路径、读写白名单、resolve 后的实际边界和中间符号链接。允许写入 `src/` 中 TS/TSX/CSS，不能读密钥或改 package.json。提示词说明权限，Python 检查落实权限；本地限制仍不等同于容器或操作系统沙箱。

`diff()` 暂存 src 后读取 cached diff，把新建文件也纳入交付。暂存不是提交。`deliver()` 检查有改动且 typecheck/build 全通过才调用 `commit()`；失败则保留目录和报告。Agent 没有自动 push、merge 或提交 PR 的工具。

公开 GitHub 是一个包含 Agent、CRM 基线和 mock 的大项目仓库；运行时的 CRM 本地仓库供 worktree 使用。两者的用途见 [Git 交付流程图](../../docs/项目流程图.md) 和 [任务分支说明](../../docs/任务分支说明.md)。

## 8. 任务页面为何这样轮询

`TaskPage` 请求结束后再用 `setTimeout` 安排下一轮，避免 `setInterval` 在慢网络中堆积请求。queued/running 正常约三秒更新；网络失败逐步延长到十五秒；404 和任务终态停止常规轮询。

- `revision`：快照版本号，任何状态/事件更新都会增加，旧响应不能覆盖新状态。
- `seq`：单任务日志顺序和 React 列表 key，时间相同的事件仍有确定顺序。
- effect 清理中的 `cancelled`：忽略卸载/切任务后的旧响应；并非取消后台任务。
- `connection` 与 `task.status`：网页断网不等于后台执行失败。
- `changes.diff` 按需作为文本读取并缓存；JSON 请求封装不能用于文本产物。
- 预览按钮看 build 是否通过；succeeded 并不表示视觉比对或浏览器功能测试完成，`not_run` 保持可见。

## 10. 用测试巩固理解

在 `design-agent/` 执行 `uv run pytest -q`，在 `design-agent/frontend/` 执行 `npm run build`。这两项不提交新的开发任务、不调用付费模型。

[test_mvp.py](../tests/test_mvp.py) 用真实临时 Git/SQLite 验证材料校验、幂等、文件隔离、修复上限、中断和串行 Worker；模型/检查结果使用确定性替身。[test_models.py](../tests/test_models.py) 用 HTTP mock 验证 GLM 推理字段的工具往返、原图请求内容和视觉失败行为。离线通过不能证明远程服务可用或 UI 还原准确。

学习时可只读观察 `runtime/tasks/<id>/` 的 `prd-extracted.md` → `design-spec.md` → `plan.json` → `agent-summary.md` → `typecheck.log/build.log` → `changes.diff` → `report.json`，将各文件和六阶段图逐一对应。想验证新的需求行为时，再通过网页提交材料并人工检查预览；该操作会使用配置的模型额度。
