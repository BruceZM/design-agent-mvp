# Agent 后台代码流程

这份指南只追踪后台 Agent 运行时的函数调用和数据流。从 `Workflow.run()` 开始读，再进入每个节点调用的具体方法。

## 1. 任务如何进入 Agent

[main.py](../backend/app/main.py) 的 `submit()` 保存上传材料并创建 queued 任务，然后调用 `worker.notify()`。此时只是接收任务，尚未完成开发。

[worker.py](../backend/app/worker.py) 的 `loop()` 从 SQLite 取最早 queued 任务，调用 `Workflow(...).run()`。同一线程等待这一条执行结束，才处理下一条。

```text
submit() → Store.create() → Worker.notify()
                                 ↓
Worker.loop() → Workflow(...).run()
                                 ↓
materials → prepare → plan → develop → check → deliver
                              ↑          │
                              └─有限修复─┘
```

## 2. `Workflow.run()`：把执行顺序连起来

代码：[workflow.py](../backend/app/workflow.py)，定位 `Workflow.run`。

- `StateGraph(State)` 声明节点之间共享的数据形状。
- `add_node()` 注册六个同名方法；`add_edge()` 声明固定执行顺序。
- `add_conditional_edges("check", ...)` 根据检查结果返回 develop 或 deliver。
- `compile().invoke({})` 从空状态同步运行这张图，直到结束或抛出异常。

这里的 `State` 逐步包含 `prd`、`design_spec`、`plan`、`checks`、`attempt`、`summary`。每个节点只返回自己新增/更新的字段，LangGraph 将它们合并给下一节点；不用每次重传所有字段。

## 3. `materials()`：把输入变成模型可用的材料

调用顺序：

```text
Workflow.materials()
  ├─ parse_prd()                       → PRD 纯文字
  ├─ describe_image()                  → 中文视觉说明
  │    └─ create_model(vision=True)
  │         └─ model.ainvoke(原图 + 解析要求)
  └─ 返回 {prd, design_spec, attempt: 0}
```

定位 [documents.py](../backend/app/documents.py) 的 `parse_prd`：将 MD/TXT/DOCX/文字 PDF 统一为字符串。

定位 [vision.py](../backend/app/vision.py) 的 `describe_image`：原图以 base64 data URI 放入多模态请求，GLM 输出设计说明。后台是同步线程，因此 `materials()` 用 `asyncio.run()` 等待异步视觉调用完成。图片只提供视觉参考，功能和交互仍以 PRD 为准。

产物：`prd-extracted.md`、`design-spec.md`。后面的计划和编码读取这两个结果，不在每一轮编码调用中重复发送原图。

## 4. `prepare()`：准备本次任务的代码环境

调用 [repository.py](../backend/app/repository.py) 的 `Repository.prepare(task_id)`：读取固定 main 提交，创建 `design-agent/<id>` 分支和独立 worktree，复用已安装依赖。

随后构造 [agent.py](../backend/app/agent.py) 的 `Developer`，其中建立 `Budget` 和编码模型。Developer 保存在 Workflow 实例上，首次开发及修复共用同一个对象、分支和预算。

这一步使模型之后写入的是本次任务的工作目录，主目录的业务基线不会被直接改动。

## 5. `plan()`：模型输出计划，代码验证计划

```text
Workflow.plan()
  → Developer.plan(prd, design_spec)
      → Budget.consume()
      → 读取 README 和文件列表
      → model.bind(JSON mode).invoke(...)
      → Plan.model_validate_json(...)
      → Repository.path(file, write=True) 逐项校验
  → 返回 {plan}，保存 plan.json
```

定位 [agent.py](../backend/app/agent.py) 的 `Plan` 和 `Developer.plan`。模型返回 summary、files、steps、acceptance；Pydantic 检查字段和数量，Repository 检查文件是否在允许写入的范围。不能仅凭模型说“计划合法”就进入开发。

## 6. `develop()`：模型选择工具，本地代码实际修改

这是 Agent 最核心的部分，定位 [agent.py](../backend/app/agent.py) 的 `Developer.develop`。

1. 用闭包绑定本任务的 Repository、日志和 Budget，定义五个 `@tool` 工具。
2. `create_agent()` 将模型、五个工具和预算中间件组成内部模型/工具循环，此时还没有发送模型请求。
3. 预读 README、类型文件和计划涉及的源码，组装 PRD、视觉说明、计划和代码上下文，再用 `agent.invoke()` 开始执行。
4. 每次模型调用前，`enforce_budget` 中间件先检查并消耗预算，再调用 `handler(request)`。
5. 模型返回 `tool_calls` 时，框架执行对应 Python 工具，将结果作为 `ToolMessage` 追加，再调用模型。
6. 模型不再请求工具时，返回开发摘要，外层 Workflow 才继续独立检查。

```text
上下文 → 预算检查 → GLM
  有 tool_calls → 本地工具执行 → ToolMessage → 下一轮预算检查 / GLM
  无 tool_calls → 开发摘要 → 外层 check
```

| 工具 | 实际调用 | 作用 |
| --- | --- | --- |
| `list_files` | `repo.files()` | 列出允许读取的文件 |
| `read_file` | `repo.read()` | 修改前了解现有代码 |
| `write_file` | `repo.write()` | 保存完整文件或创建新文件 |
| `replace_text` | `repo.read()` → 唯一匹配 → `repo.write()` | 精确局部修改 |
| `run_check` | `repo.check()` | 只运行 typecheck/build |

模型只产生工具名称和参数，真正的文件操作由 Repository 执行。`Repository.path()` 限制相对路径、src 白名单和符号链接；`safely()` 把可纠正的文件错误返回给模型，预算或模型异常则向外抛出。

外层 `Workflow` 控制六个阶段；内部 `create_agent` 控制模型和工具往返。这是两层执行循环。

## 7. 模型适配在什么位置生效

代码：[models.py](../backend/app/models.py)。视觉和 Developer 都通过 `create_model()` 建立 GLM 客户端。

`GLMChatOpenAI._create_chat_result()` 在解析非流式响应时保留 `reasoning_content`；`_get_request_payload()` 在下一轮 assistant 消息中重新放回这个字段，让连续工具调用保留所需的思考上下文。

`Budget` 统计 plan、develop 和修复中的调用，**不包含 materials 的视觉请求**。修复不会清零预算，模型请求也没有 SDK 自动重试。

## 8. `check()` 与 `route_checks()`：检查和有限修复

定位 [workflow.py](../backend/app/workflow.py) 的 `check`、`route_checks`。

`check()` 独立调用 `repo.check("typecheck")` 和 `repo.check("build")`，保存真实命令输出，并把 `attempt` 加一。即使模型摘要说已通过，仍重新检查。

- 两项通过：进入 deliver。
- 有失败且 `attempt <= max_repairs`：回到 develop，将失败检查输出交给同一个 Developer 修复。
- 修复次数用完：进入 deliver 保存失败结果。

默认 `max_repairs=1`：首次检查后的 attempt=1 允许一次修复；第二次检查后的 attempt=2 不再返回开发。

## 9. `deliver()`：保存改动并确定终态

```text
Workflow.deliver()
  → Repository.diff()                 → 暂存 src，包含新文件，取得 diff
  → 有源码改动且两项检查通过？
      是 → Repository.commit()        → succeeded
      否 → 保留分支，不提交            → failed
  → 保存 changes.diff、report.json、report.md
  → Store.update() + Store.event()
```

成功仅表示有改动且编译/构建通过。当前代码将浏览器功能与视觉验收写为 `not_run`，不能由模型摘要替代实际验收。

## 10. 状态记录和异常如何收尾

每个节点开头的 `stage()` 更新 SQLite 中的 status/phase，再调用 `event()` 追加日志；`artifact()` 保存可审阅的文本产物。具体实现位于 [store.py](../backend/app/store.py)：任务快照用 revision 标记变化，日志用 seq 保持顺序。

`Workflow.run()` 外层捕获任务异常，保存错误、已有差异和失败报告，不自动重新提交任务。Worker 重启会标记旧 running 为 interrupted；这里没有 LangGraph checkpointer，不能从中断节点续跑。

沿着这条调用链看完，再对照一个任务目录中的材料、计划、检查日志和最终 diff，就能把每一段代码与它产生的数据对应起来。
